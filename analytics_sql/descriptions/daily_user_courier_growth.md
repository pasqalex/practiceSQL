# Daily User and Courier Growth Metrics

**Задача:** построить календарь появления новых пользователей и курьеров с накопительными итогами, дневными изменениями и темпами роста.

**SQL-файл:** [daily_user_courier_growth.sql](../sql/daily_user_courier_growth.sql)

---

## Предположения о данных

- user_id в user_actions и courier_id в courier_actions не содержат NULL
- Поле time в обеих таблицах хранит timestamp создания действия
- Один пользователь или курьер может иметь множество записей, но первое появление определяется минимальным значением time
- Таблицы не обязаны пересекаться по датам: могут быть дни только с новыми пользователями, только с курьерами, или без активности обоих типов

---

## Логика решения

### 1. first_orders
Для каждого user_id находится время первого действия через минимум по полю time. Затем время приводится к дате, и по каждой дате считается количество таких пользователей.

### 2. first_delivers
Аналогично для курьеров: для каждого courier_id находится минимальное время, оно приводится к дате, и считается количество новых курьеров по дням.

### 3. daily_stats
Два потока данных склеиваются через FULL JOIN по дате. Для дней, где присутствует только одна из сторон, NULL заменяется на 0 через COALESCE. Это гарантирует, что все даты из обоих источников попадут в результат, а отсутствующие значения не сломают дальнейшие вычисления.

### 4. warp
Расчётный слой, где формируются все базовые метрики:

- накопительные итоги пользователей и курьеров через оконную функцию SUM с сортировкой по дате;
- абсолютное изменение новых пользователей и курьеров к предыдущему дню через LAG;
- процентное изменение новых пользователей и курьеров через деление на предыдущее значение.

Для всех оконных функций используется именованное окно pattern с единым порядком сортировки по дате. Это исключает дублирование конструкции ORDER BY и гарантирует консистентность вычислений.

### 5. Финальный запрос
На основе готовых накопительных итогов считаются темпы роста общей базы: отношение прироста накопительного итога к предыдущему значению. Именованное окно pattern определяется повторно на этом уровне, так как оконные спецификации не наследуются между CTE.

## Использованные методы

| Категория | Метод | Зачем |
|:---|:---|:---|
| Агрегация | MIN по времени | Определение момента первого появления сущности |
| Агрегация | COUNT с группировкой по дате | Подсчёт новых пользователей и курьеров внутри дня |
| Склейка | FULL JOIN | Сохранение всех дат из обоих потоков, даже если в одном из них дата отсутствует |
| Защита | COALESCE с нулём | Замена NULL на 0 после FULL JOIN |
| Аналитика | SUM с оконной спецификацией ORDER BY | Накопительный итог по дате |
| Аналитика | LAG | Доступ к значению предыдущей строки для расчёта изменений |
| Аналитика | Именованное окно WINDOW | Централизованное определение порядка строк для всех оконных функций в одном запросе |
| Защита | NULLIF с нулём | Предотвращение деления на ноль при отсутствии предыдущего значения |
| Форматирование | ROUND | Округление процентных изменений до двух знаков |

## Защита от краевых случаев

| Ситуация | Решение |
|:---|:---|
| День с пользователями, но без курьеров | FULL JOIN сохраняет строку, COALESCE заменяет отсутствующих курьеров на ноль |
| День с курьерами, но без пользователей | Симметрично: COALESCE заменяет отсутствующих пользователей на ноль |
| Первый день в выборке | LAG возвращает NULL, деление блокируется через NULLIF, результат становится NULL вместо ошибки |
| Предыдущий день имел ноль новых сущностей | NULLIF в знаменателе предотвращает деление на ноль, возвращая NULL вместо runtime error |
| Пропуск дат в исходных данных | Запрос выводит только те дни, которые есть в данных. Пустые даты не генерируются |

## Проверка корректности

Для валидации можно сравнить сумму приростов за все даты с финальным накопительным значением. Сумма колонки new_users должна равняться максимальному значению total_users. Аналогично для курьеров: сумма new_couriers должна совпадать с максимальным total_couriers.

Также можно проверить, что накопительный итог никогда не убывает: каждое следующее значение total_users должно быть больше или равно предыдущему. Если это нарушается, значит в исходных данных есть записи с датами вне хронологического порядка или дубли user_id.

## Ограничения

- Запрос не гарантирует непрерывность календаря. Если в какой-то день не было ни пользователей, ни курьеров, эта дата отсутствует в выводе. Для анализа временных рядов с фиксированной сеткой потребуется генерация календарного справочника.
- Если один и тот же user_id появляется в таблице с разницей в несколько лет, запрос засчитает его только в день самого первого действия.
- FULL JOIN по дате предполагает, что обе таблицы используют одну и ту же временную зону. При наличии различий в хранении timezone требуется явное приведение к единому часовому поясу до извлечения даты.
- Именованное окно определяется отдельно в каждом запросе, где используются оконные функции. При изменении порядка сортировки его нужно править в двух местах.

## Применение

Когортный отчёт для оценки динамики привлечения аудитории. Накопительные кривые позволяют сравнить скорость роста пользовательской и курьерской баз на одном графике, а процентные изменения помогают выявить аномалии в отдельных днях.
