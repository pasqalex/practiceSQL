# Users and Orders per Courier

**Задача:** для каждого дня рассчитать количество платящих пользователей и заказов, приходящихся на одного активного курьера.

**SQL-файл:** [users_orders_per_courier.sql](../sql/users_orders_per_courier.sql)

---

## Предположения о данных

- user_actions содержит записи о действиях пользователей, включая создание и отмену заказов
- courier_actions содержит записи о действиях курьеров, включая принятие и доставку заказов
- Поле time в обеих таблицах хранит timestamp действия
- Один курьер может как принимать заказ, так и доставлять его
- Один заказ может проходить через несколько курьеров на разных этапах
- Отменённые заказы исключаются из расчётов пользователей и заказов

---

## Логика решения

### 1. not_canceled_orders
Извлекаются все заказы из user_actions, для которых не существует записи с действием отмены. Для каждого заказа фиксируется дата, идентификатор пользователя и время создания.

### 2. daily_users
На основе неотменённых заказов по каждой дате считается количество уникальных пользователей, совершивших заказ.

### 3. orders_per_day
По тем же неотменённым заказам подсчитывается общее количество заказов за каждый день.

### 4. count_of_active_couriers
Формируется пул активных курьеров из двух категорий:

- курьеры, принявшие заказ, при условии что этот заказ в итоге был доставлен;
- курьеры, непосредственно доставившие заказ.

Обе категории объединяются через UNION ALL, внешний запрос выполняет дедупликацию по идентификатору курьера внутри каждой даты. Использование UNION ALL вместо UNION обосновано тем, что дедупликация всё равно происходит на уровне агрегатной функции.

### 5. Финальный запрос
Три независимых потока данных склеиваются через цепочку FULL JOIN по дате. Для дней, где присутствует только часть метрик, отсутствующие значения заменяются через COALESCE.

Рассчитываются две метрики эффективности курьерского пула:
- отношение количества платящих пользователей к количеству активных курьеров;
- отношение общего числа заказов к количеству активных курьеров.

Результат округляется до двух знаков после запятой.

---

## Использованные методы

| Категория | Метод | Зачем |
|:---|:---|:---|
| Фильтрация | NOT EXISTS | Исключение отменённых заказов из расчётов пользователей и заказов |
| Агрегация | COUNT DISTINCT | Подсчёт уникальных пользователей и курьеров внутри дня |
| Агрегация | COUNT с группировкой | Подсчёт общего числа заказов по дням |
| Объединение | UNION ALL | Сбор курьеров из двух независимых категорий активности без промежуточной дедупликации |
| Склейка | FULL JOIN | Сохранение всех дат из трёх независимых потоков |
| Защита | COALESCE | Замена NULL на исходное значение после FULL JOIN |
| Защита | NULLIF с нулём | Предотвращение деления на ноль в дни без активных курьеров |
| Форматирование | ROUND | Округление метрик до двух знаков |
| Приведение типов | CAST к DECIMAL | Корректное деление с дробной частью, переносимо между диалектами SQL |

## Защита от краевых случаев

| Ситуация | Решение |
|:---|:---|
| День с заказами, но без курьеров | FULL JOIN сохраняет строку, NULLIF в знаменателе предотвращает ошибку деления на ноль |
| День с курьерами, но без заказов | Симметрично: FULL JOIN сохраняет дату, COALESCE заменяет отсутствующие заказы и пользователей на NULL |
| День без активности обоих типов | Отсутствует в выводе, так как не порождает строк ни в одном из потоков |
| Курьер присутствует в обеих категориях UNION ALL | Внешний COUNT DISTINCT дедуплицирует, курьер засчитывается один раз |
| Заказ был принят, но не доставлен | Курьер не попадает в первую категорию, так как фильтр требует наличия доставки по заказу |

---

## Проверка корректности

Для валидации можно сравнить сумму daily_orders за все даты с общим количеством строк в not_canceled_orders. Также можно проверить, что users_per_courier не превышает orders_per_courier логически, так как на одного пользователя может приходиться несколько заказов.

---

## Ограничения

- Запрос не гарантирует непрерывность календаря. Дни без заказов, пользователей и курьеров отсутствуют в выводе.
- Активность курьеров определяется по принятию или доставке заказов. Если бизнес-логика требует учитывать другие статусы, потребуется расширение условий отбора.
- FULL JOIN по дате предполагает, что все таблицы используют одну и ту же временную зону. При различиях в хранении timezone требуется явное приведение к единому часовому поясу до извлечения даты.

## Применение

Метрики позволяют оценивать загрузку курьерского пула и баланс спроса с предложением. Рост orders_per_courier при стабильном users_per_courier сигнализирует о повышении частоты заказов от постоянных клиентов. Снижение обеих метрик при росте числа курьеров может указывать на избыток логистических мощностей.
