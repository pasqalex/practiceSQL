# Single vs Several Orders Users Share

**Задача:** для каждого дня определить долю пользователей, сделавших ровно один заказ, и долю пользователей, сделавших несколько заказов, от общего числа платящих пользователей.

**SQL-файл:** [single_vs_several_orders_share.sql](../sql/single_vs_several_orders_share.sql)

---

## Предположения о данных

- user_actions содержит записи о действиях пользователей, включая создание и отмену заказов
- Поле time хранит timestamp действия
- Один пользователь может совершать несколько заказов в один день
- В таблице courier_actions данные не используются, анализ только по пользователям
- Отменённые заказы исключаются из расчётов

---

## Логика решения

### 1. not_canceled_orders
Извлекаются все заказы из user_actions, для которых не существует записи с действием отмены. Для каждого заказа фиксируется дата и идентификатор пользователя.

### 2. count_of_orders
На основе неотменённых заказов для каждой пары пользователь-плюс-дата считается количество заказов. Это позволяет определить, сколько заказов совершил конкретный пользователь в конкретный день.

### 3. order_stats
По каждой дате формируются три метрики:

- общее количество уникальных платящих пользователей;
- количество пользователей, сделавших ровно один заказ;
- количество пользователей, сделавших несколько заказов.

Фильтрация по количеству заказов выполняется через агрегатную фильтрацию.

### 4. Финальный запрос
Рассчитываются доли от общего числа платящих пользователей. Результат округляется до двух знаков после запятой.

---

## Использованные методы

| Категория | Метод | Зачем |
|:---|:---|:---|
| Фильтрация | NOT EXISTS | Исключение отменённых заказов |
| Агрегация | COUNT с группировкой по пользователю и дате | Подсчёт заказов на одного пользователя внутри дня |
| Агрегация | COUNT DISTINCT | Подсчёт уникальных платящих пользователей по дню |
| Агрегация | Агрегатная фильтрация FILTER | Разделение пользователей на однозаказных и многозаказных в рамках одного GROUP BY |
| Защита | NULLIF с нулём | Предотвращение деления на ноль в дни без платящих пользователей |
| Форматирование | ROUND | Округление долей до двух знаков |
| Приведение типов | CAST к DECIMAL | Корректное деление с дробной частью, переносимо между диалектами SQL |

---

## Защита от краевых случаев

| Ситуация | Решение |
|:---|:---|
| День без платящих пользователей | NULLIF в знаменателе возвращает NULL вместо ошибки деления на ноль |
| Пользователь с нулём заказов | Не возникает, так как считаются только неотменённые заказы из исходной таблицы |
| Первый день в выборке | Расчёт долей происходит в рамках одной строки, не требует предыдущих значений |
| Отменённые заказы | NOT EXISTS полностью исключает заказ из всех расчётов, если найдено действие cancel_order |

---

## Проверка корректности

Для валидации можно проверить, что сумма долей single_order_users_share и several_orders_users_share за каждый день равна 100 при условии, что paying_users больше нуля. Если сумма отличается, это сигнал о некорректных исходных данных или пропусках в логике фильтрации.

Также можно сравнить paying_users с суммой single_orders и several_orders. Эти значения должны совпадать, так как каждый платящий пользователь попадает ровно в одну из двух категорий.

```
     single_orders + several_orders = paying_users as total_check
```

---

## Ограничения

- Запрос считает заказы внутри одного дня. Если пользователь сделал два заказа в разные дни, в каждом из этих дней он будет учтён как однозаказный для соответствующей даты. Для когортного анализа за весь период требуется другая гранулярность группировки.
- Агрегатная фильтрация FILTER доступна в PostgreSQL и некоторых других СУБД, но не является частью стандарта SQL. При миграции на другую систему может потребоваться замена на конструкцию CASE WHEN внутри SUM или COUNT.
- Запрос не различает частично отменённые заказы. Если заказ был создан, а затем отменён, он исключается полностью, даже если имелись промежуточные действия.

## Применение

Отчёт позволяет оценивать поведенческие паттерны аудитории. Высокая доля однозаказных пользователей может указывать на проблемы с удержанием или на приток новой аудитории. Рост доли многозаказных пользователей сигнализирует о повышении вовлечённости и лояльности клиентской базы.
