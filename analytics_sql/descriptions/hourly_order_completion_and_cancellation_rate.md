# Hourly Order Completion and Cancellation Rate

**Задача:** для каждого часа суток посчитать количество успешных заказов, отменённых заказов и процент отмен.

**SQL-файлы:**
- [`hourly_cancel_rate_left_join.sql`](../sql/hourly_cancel_rate_left_join.sql) — вариант с одним проходом по таблице заказов
- [`hourly_cancel_rate_two_scans.sql`](../sql/hourly_cancel_rate_two_scans.sql) — вариант с двумя независимыми проходами

---

## Предположения о данных

- Таблица заказов содержит временную метку создания с точностью до секунды
- Таблица действий пользователя содержит только два типа записей: создание заказа и отмена заказа
- Один заказ может иметь ровно одну запись отмены или не иметь её вовсе
- Временная зона в таблицах единая, извлечение часа производится напрямую из timestamp

---

## Варианты решения

### Вариант 1: LEFT JOIN с агрегатной фильтрацией
Выполняется один проход по таблице заказов. Каждая строка соединяется с предварительно построенным списком отменённых заказов через LEFT JOIN. Внутри группировки по часу суток две агрегатные функции с условием FILTER разделяют общий поток на успешные и отменённые заказы. Процент отмен считается в том же SELECT.

### Вариант 2: Два независимых CTE
Формируются два отдельных подзапроса, каждый из которых сканирует таблицу заказов самостоятельно. Первый подзапрос исключает отмены через Hash Anti Join и группирует оставшиеся заказы по часу. Второй подзапрос включает только отмены через Hash Join и также группирует по часу. Результаты двух потоков склеиваются через FULL JOIN, а финальный SELECT считает процент относительно суммы обеих категорий.

---

## Сравнение производительности

| Аспект | Вариант 1 (LEFT JOIN) | Вариант 2 (Два CTE) |
|:---|:---|:---|
| Чтение таблицы заказов | Один Seq Scan | Два Seq Scan |
| Объём чтения из кэша | ~613 страниц | ~1226 страниц |
| Тип агрегации | GroupAggregate с предварительной сортировкой | Два HashAggregate |
| Сортировка | External merge sort, ~840 KB на диск | Только финальная сортировка 24 строк в памяти |
| Временные файлы | Есть (чтение и запись на диск) | Нет |
| JIT-компиляция | Не применяется | ~46 мс (почти четверть общего времени) |
| Execution Time | ~93 мс | ~190 мс |

### Почему LEFT JOIN быстрее
Экономия на чтении таблицы заказов компенсирует накладные расходы на построение хэш-таблицы соединения. Даже с учётом сортировки перед агрегацией запрос выполняется почти вдвое быстрее, так как избегает второго полного сканирования таблицы.

### Почему два CTE медленнее
Двойное сканирование таблицы удваивает объём чтения. Кроме того, планировщик включает JIT-компиляцию (преобразование запроса в машинный код на лету), что для коротких запросов даёт отрицательный эффект: затраты на компиляцию превышают выигрыш от неё.

### Скрытая проблема LEFT JOIN
Планировщик плохо оценивает кардинальность выражения извлечения часа из timestamp, принимая его за почти уникальное значение. Из-за этого вместо HashAggregate выбирается GroupAggregate, требующий предварительной сортировки всех строк. На текущем объёме данных сортировка уходит на диск (external merge sort), но остаётся быстрее, чем двойное сканирование. При росте таблицы стоит следить за увеличением временных файлов.

### Когда два CTE могут быть предпочтительнее
Если доля отменённых заказов приближается к 50 % и хэш-таблица отмен перестаёт помещаться в оперативную память (work_mem), раздельные проходы с фильтрацией на лету могут оказаться эффективнее, чем построение большого хэш-индекса для соединения.

## Использованные методы

| Категория | Метод | Зачем |
|:---|:---|:---|
| Фильтрация | NOT EXISTS / LEFT JOIN | Исключение отменённых заказов |
| Соединение | LEFT JOIN | Одновременный доступ к факту отмены и данным заказа |
| Соединение | FULL JOIN | Склейка двух независимых потоков без потери часов |
| Агрегация | FILTER | Разделение одного потока на две метрики в рамках одной группировки |
| Агрегация | COUNT | Подсчёт заказов по категориям |
| Защита | NULLIF | Предотвращение деления на ноль в часах без заказов |
| Форматирование | ROUND | Округление процента отмен до трёх знаков |
| Приведение типов | CAST к DECIMAL | Корректное дробное деление |

## Защита от краевых случаев

| Ситуация | Решение |
|:---|:---|
| Час без заказов | FULL JOIN в варианте 2 сохраняет час, LEFT JOIN в варианте 1 возвращает NULL, который можно заменить на ноль через COALESCE |
| Час только с отменами или только с успешными | FULL JOIN в варианте 2 сохраняет обе стороны, в варианте 1 FILTER корректно распределяет строки |
| Все заказы в часе отменены | NULLIF в знаменателе предотвращает ошибку деления на ноль |
| Отсутствие заказов вообще | NULLIF возвращает NULL вместо runtime error |

## Ограничения

- Оба варианта полагаются на точность часовой метки в поле создания заказа. Если заказ создан в 23:59, а отменён в 00:01, он попадёт в час 23 для успешных/отменённых подсчётов.
- Вариант 1 чувствителен к оценке кардинальности функции извлечения часа. При миграции на другую СУБД планировщик может выбрать иную стратегию агрегации.
- Вариант 2 при росте таблицы заказов линейно увеличивает объём чтения, так как сканирует таблицу дважды.
- Оба варианта не гарантируют непрерывность 24 часов: если в какой-то час не было ни одного заказа, этот час отсутствует в выводе.

## Применение

Отчёт позволяет выявлять часы пиковой нагрузки и часы с аномальным процентом отмен. Рост cancel_rate в определённый час может сигнализировать о технических сбоях, нехватке курьеров или проблемах с приёмом заказов в конкретный интервал.
