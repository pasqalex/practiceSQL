# Daily Paying Users and Active Couriers Share

**Задача:** построить ежедневный отчёт о количестве платящих пользователей, активных курьеров, новых регистрациях обеих категорий и доле активных участников от накопительной базы.

**SQL-файл:** [daily_paying_users_couriers_share.sql](../sql/daily_paying_users_couriers_share.sql)

---

## Предположения о данных

- user_id в user_actions и courier_id в courier_actions не содержат NULL
- Поле time в обеих таблицах хранит timestamp действия
- В user_actions присутствуют только записи create_order и cancel_order
- Один пользователь или курьер может иметь множество записей, но первое появление определяется минимальным значением time
- Таблицы user_actions и courier_actions не обязаны пересекаться по датам: могут быть дни только с пользователями, только с курьерами, или без активности обоих типов

---

## Логика решения

### 1. not_canceled_orders
Извлекаются все заказы из user_actions, для которых не существует записи с action равным cancel_order. Для каждого заказа фиксируется дата и идентификатор пользователя.

### 2. count_of_paying_users
На основе неотменённых заказов по каждой дате считается количество уникальных пользователей, совершивших заказ.

### 3. count_of_active_couriers
К неотменённым заказам подключается таблица courier_actions. По каждой дате считается количество уникальных курьеров, которые доставляли эти заказы.

### 4. first_orders
Для каждого user_id находится дата первого действия в системе. Затем по каждой дате подсчитывается, сколько новых пользователей появилось.

### 5. first_delivers
Аналогично для курьеров: дата первого действия каждого courier_id и количество новых курьеров по дням.

### 6. daily_stats
Четыре независимых потока данных склеиваются через цепочку FULL JOIN по дате. Для дней, где присутствует только часть метрик, отсутствующие значения заменяются на ноль через COALESCE. Дата формируется через COALESCE по всем четырём источникам, чтобы не потерять дни, где активность была только с одной стороны.

### 7. warp
Расчётный слой, где формируются накопительные итоги новых пользователей и курьеров. Оконная функция SUM с сортировкой по дате считает общее количество зарегистрированных участников на каждый день. Именованное окно pattern централизует определение порядка строк.

### 8. Финальный запрос
На основе накопительных итогов считаются доли активных пользователей и курьеров от общей базы. Отношение платящих пользователей к total_users и активных курьеров к total_couriers даёт процент вовлечённости накопленной аудитории.

## Использованные методы

| Категория | Метод | Зачем |
|:---|:---|:---|
| Фильтрация | NOT EXISTS | Исключение отменённых заказов |
| Агрегация | COUNT DISTINCT | Подсчёт уникальных пользователей и курьеров внутри дня |
| Агрегация | MIN по времени | Определение даты первого появления сущности |
| Склейка | FULL JOIN | Сохранение всех дат из четырёх независимых потоков |
| Защита | COALESCE с нулём | Замена NULL на 0 после FULL JOIN |
| Аналитика | SUM с оконной спецификацией ORDER BY | Накопительный итог по дате |
| Аналитика | Именованное окно WINDOW | Централизованное определение порядка строк для всех оконных функций в одном запросе |
| Защита | NULLIF с нулём | Предотвращение деления на ноль при отсутствии накопленной базы |
| Форматирование | ROUND | Округление долей до двух знаков |

## Защита от краевых случаев

| Ситуация | Решение |
|:---|:---|
| День с платящими пользователями, но без курьеров | FULL JOIN сохраняет строку, COALESCE заменяет отсутствующих курьеров на ноль |
| День с курьерами, но без пользователей | Симметрично: COALESCE заменяет отсутствующих пользователей на ноль |
| День с новыми регистрациями, но без активности | FULL JOIN с четырьмя источниками сохраняет дату, COALESCE по всем четырём колонкам даты гарантирует попадание в результат |
| Первый день в выборке | Накопительная сумма начинается с текущего значения, NULL в знаменателе блокируется через NULLIF |
| Накопленная база равна нулю | NULLIF в знаменателе предотвращает деление на ноль, возвращая NULL вместо ошибки |

## Проверка корректности

Для валидации можно сравнить сумму приростов новых пользователей за все даты с финальным накопительным значением. Сумма колонки new_users должна равняться максимальному значению total_users. Аналогично для курьеров: сумма new_couriers должна совпадать с максимальным total_couriers.

Также можно проверить, что paying_users_share и active_couriers_share не превышают 100 при корректных данных. Если доля вышла за этот предел, это сигнал о расхождении между active_couriers и not_canceled_orders.

---

## Ограничения

- Запрос не гарантирует непрерывность календаря. Если в какой-то день не было ни пользователей, ни курьеров, ни новых регистраций, эта дата отсутствует в выводе. Для анализа временных рядов с фиксированной сеткой потребуется генерация календарного справочника.
- first_orders и first_delivers считают первое действие в системе без фильтрации отмен. Если бизнес-логика требует учитывать только первый неотменённый заказ, потребуется связка с not_canceled_orders.
- FULL JOIN по дате предполагает, что все таблицы используют одну и ту же временную зону. При различиях в хранении timezone требуется явное приведение к единому часовому поясу до извлечения даты.
- Именованное окно определяется отдельно в каждом запросе, где используются оконные функции. При изменении порядка сортировки его нужно править в двух местах.

## Применение

Отчёт позволяет оценивать вовлечённость накопленной базы пользователей и курьеров. Снижение paying_users_share сигнализирует о том, что рост аудитории опережает активность, тогда как рост active_couriers_share может указывать на улучшение логистики или увеличение числа доставок.
