# Daily Revenue Growth

**Задача:** посчитать ежедневную выручку и её изменение по сравнению с предыдущим днём.

**SQL-файл:** [`daily_revenue_growth.sql`](../sql/daily_revenue_growth.sql)

---

## Логика решения

Запрос разбит на три слоя: фильтрация заказов, агрегация выручки по дням и расчёт динамики.

### 1. Исключение отменённых заказов

Сначала извлекаем все `order_id`, по которым есть действие `cancel_order`. Затем через `NOT EXISTS` оставляем только те заказы, которых нет в этом списке.

Метод `NOT EXISTS` выбран сознательно: он корректно работает даже при потенциальных `NULL` в ключах и семантически точно выражает «отмены нет».

### 2. Расчёт дневной выручки

На основе отфильтрованных заказов строим производную таблицу:

- массивы товаров `product_ids` разворачиваются через `UNNEST` в отдельные строки;
- к каждому товару подтягивается цена из справочника;
- данные группируются по дате создания заказа (`order_date`);
- суммируются цены товаров.

Результат - одна строка на каждый календарный день с общей выручкой.

### 3. Расчёт динамики

К готовой дневной выручке в финальном `SELECT` применяется оконная функция `LAG`, которая «смотрит» на предыдущий день без объединения таблицы самой с собой.

На её основе считаются два показателя:

- абсолютное изменение (`текущий день − предыдущий день`);
- процентное изменение (`(текущий − предыдущий) / предыдущий × 100`).

---

## Использованные методы

| Метод | Зачем |
|:---|:---|
| **CTE (`WITH`)** | Декомпозиция: фильтрация отдельно от агрегации |
| **`NOT EXISTS`** | Надёжное исключение отменённых заказов |
| **`UNNEST`** | Разворачивание массива товаров в плоский список |
| **`SUM` + `GROUP BY`** | Агрегация цен до уровня дня |
| **`LAG`** | Доступ к значению предыдущей строки (вчерашней выручке) |
| **`COALESCE`** | Замена `NULL` на `0` для первого дня в выборке |
| **`ROUND`** | Округление итоговых метрик до одного знака |

---

## Защита от краевых случаев

| Ситуация | Решение |
|:---|:---|
| **Первый день в выборке** | У `LAG` нет предыдущего значения → `NULL`. `COALESCE` заменяет его на `0`, чтобы не ломать арифметику |
| **Деление на ноль** | Формула процента строится как `(a − b) / b`, где `b` - выручка предыдущего дня. Если предыдущего дня нет, `COALESCE` уже обнуляет всю формулу до применения процента |
| **`NULL` в ключах** | `NOT EXISTS` корректно обрабатывает отсутствие записи, в отличие от `NOT IN`, который «ломается» на `NULL` |

| Колонка | Описание |
|:---|:---|
| `order_date` | Дата |
| `daily_revenue` | Выручка за день |

## Примечания по производительности

- **`UNNEST` в подзапросе** - разворачивание массива происходит до соединения с таблицей цен. Это позволяет оптимизатору строить план на основе реального количества товарных позиций.
- **Оконная функция вместо self-JOIN** - `LAG` вычисляется за один проход по уже агрегированным данным. Нет необходимости материализовать промежуточный результат или джойнить таблицу саму на себя.
- **Индексы, которые помогут:** `user_actions(order_id, action)` для быстрого поиска отмен, `orders(creation_time)` если таблица заказов большая, `products(product_id)` для соединения по ценам.

---

## Вывод

Запрос позволяет отслеживать динамику выручки в ежедневной разбивке и быстро выявлять аномалии - как резкие падения, так и всплески продаж. Структура легко масштабируется: при необходимости можно добавить `PARTITION BY` (например, по категории товара или региону), не меняя архитектуру фильтрации заказов.
